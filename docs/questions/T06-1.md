### Q1 Jev 决策请求在本机经常 3 秒超时、降级到 llm / mock — Cursor — T06
- 类型：疑问（疑似流水线 / 网络问题，给 Codex 看）
- 背景：评测里 `decide()` 走 Jev 时，`OpenRouter /alpha/decisions timed out after 3000ms` 频繁出现，随后降级到 `CLASSIFIER_LLM_MODEL`（5.9 秒超时）或 mock。实测数据：
  - 完整评测 3 次：第一次尝试就被降级的用例分别为 3 / 5 / 7 条（共 60 条）；脚本退避 3 秒、6 秒重试后，仍降级的分别为 1 / 2 / 1 条。
  - 单独调用 `decide({}, "这件大衣是纯羊毛的吗", { provider: "jev" })`：第一次 8985 ms，降级成 mock（other 0.55）；同一轮里「到哪了」2378 ms、「真丝的衣服可以丢洗衣机吗」1914 ms 是 Jev 正常返回。
  - 降级发生在刚重置完（RAG 重建耗时 20–40 秒）之后的头几条、以及 Jev 保温（`JEV_KEEPALIVE_MS`）间隔内偶发。成功时 Jev 约 0.37–0.45 秒，和 T01b 一致。
  - 影响：被降级的消息在 trace 里 `decideProvider` 变成 llm / mock，意图置信度和风险分数是别的后端给的；买家侧最长等待约 9 秒（`DECIDE_BUDGET_MS`）。评测报告里 L2 的 p95 延迟 8955 ms 就是这么来的。
- 建议：Codex 看一下：① Jev 请求 3 秒上限是否偏紧（冷路径实测 ≈ 6 秒，见 T01b）；② 首次请求前是否可以在 `startJevWarmup()` 完成后再放行第一条（或重置后主动再预热一次）；③ 失败后的第二次 Jev 重试是否比直接降级到 5.9 秒的 llm 更划算。
- 临时方案（我现在怎么继续的）：不改 `lib/brain/**`。评测脚本对"最终仍被降级"的用例单独标注原因「分类器降级」，并且不把它们算进「Jev 中文表现」统计；总成绩里照实计入。降级的用例会退避重试最多 2 次，报告里写明第一次降级的条数。
