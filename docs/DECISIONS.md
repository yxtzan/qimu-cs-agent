# DECISIONS — 架构决策记录

> 由 Claude（总指挥）维护。每条记录：做了什么决定、为什么、放弃了什么。面试时被问"为什么这么设计"，答案就在这里。

### D001 风险检测做成旁路闸门，而不是漏斗的一层
- 决定：每条买家消息都并行跑风险检测（Jev Noul × 4 + 情绪 Score），命中直接转人工，不管本该走哪一层。
- 原因：漏斗按**成本**排序，风险按**严重度**排序，是两条正交的轴。如果把风险放进漏斗，L1 规则命中的消息（比如点了"退款进度"按钮后又骂人/威胁投诉）就会绕过风险检查。
- 代价：每条消息多一次 Jev 调用，成本可忽略。
- 2026-10-04 修订：T01 实测 Jev 单次约 6.4 秒，如果 L1 也等它，L1 的毫秒级优势就没了。改为风险闸门分两段：硬关键词同步检查（覆盖全部消息）+ 模型风险分（L1 命中时异步，先回复、命中再追加转人工；L1 未命中时同步）。代价是极少数情况下 L1 先回了一句、几秒后才转人工，对演示可接受，看板上也能如实展示。

### D002 三层只管"理解"，"执行"交给 handler
- 决定：L1/L2/L3 决定的是"这句话是什么意图、该谁处理"。生成回复是 handler 的事：L2 判为 `product_consult` 后，handler 仍可调用 RAG + LLM 生成答案。
- 原因：「上下文层不上大模型」只对理解环节成立。售前咨询必须靠知识库 + 生成才能答好。
- 看板统计时区分：`understandingLayer`（谁理解的）和 `generation`（是否调用了 LLM 生成）。

### D003 对话状态由代码维护，模型无状态
- 决定：`DialogState` 由流水线在每条消息到来时先更新，再序列化成文本喂给分类器。Jev 不记忆任何东西。
- 原因：可解释、可调试、可在卖家端展示；换分类器实现不影响状态逻辑。
- 补充：买家从订单页/商品页进入客服时，前端带上 `context.orderId / productId`，直接预填槽位——很多指代问题在产品设计上就消除了，不需要模型去猜。

### D004 分类器统一接口，三种实现可切换
- 决定：`classify()` 一个接口，`CLASSIFIER_PROVIDER=jev | llm | mock`。
- 默认 Jev，运行时自动降级 jev → llm → mock（规则见 ARCHITECTURE.md §4.3）。
- 2026-10-03 更新：团队决定**取消前置的 Jev 中文测试**，直接以 Jev 为主力，时间优先。
- 代价与对策：Jev 以英文为主，中文效果未经前置验证。对策是低置信度自动掉到 L3、风险闸门有硬关键词兜底、T06 评测补测中文表现并据此调阈值。另一个代价是阈值在评测集上调，评测分数会**偏乐观**，演示时如实说明。

### D005 不用数据库软件，JSON 文件 + 内存
- 决定：`data/seed/*.json` 为种子，运行时写 `data/runtime/*.json`。
- 原因：36 小时 Demo、团队不写代码，零安装成本最重要。数据层封装在 `lib/store`，以后换 Supabase/Postgres 只改这一层。
- 代价：不能部署到无状态的 Serverless 平台持久化写入；演示在本机运行。

### D006 写操作必须买家确认
- 决定：退款、换货、改地址、取消订单这类写操作，工具层只生成 `PendingAction`，买家点「确认」后才执行。
- 原因：客服 Agent 最大的风险是"自作主张"。这也是演示时的一个亮点。

### D007 卖家端 = 移动端优先的 Web + PWA
- 决定：先做 `/seller` 移动端 Web，加 manifest 成为 PWA，手机"添加到主屏幕"即可像 app 一样使用。
- 原因：36 小时内做原生 app 不现实；后续可用 Capacitor 打包，代码不用重写。

### D008 店铺品类：服饰女装
- 决定：虚构「栖木 QIMU 女装」。
- 原因：尺码咨询、换码、材质洗护、退换货、物流催单覆盖了售前/售中/售后全部典型场景。

### D010 Jev 实测延迟远高于宣传值，先测量再定 L2 方案
- 事实：T01 实测 Jev（OpenRouter Decisions API，7 题一次请求）单次约 6.4 秒，成本约 $0.000059（¥0.0004）；官方宣传 70–500ms。LLM 兜底模型因开着思考模式超过 8 秒。
- 决定：先做 T01b 测量（拆题、并行、换路径、关思考、对照组），用数据决定 L2 意图分类和风险检测各用什么。同时立刻做两件不依赖结论的事：L1 不等模型（D001 修订）；所有 LLM 默认关闭思考、`decide()` 设总时限。
- 对演示叙事的影响：如果 Jev 降不下来，"三层漏斗"的卖点从"又快又省"调整为"省 + 可控 + 校准概率可做阈值"，延迟优势由 L1 和关闭思考的小模型承担。看板如实展示各层延迟。
- **结论（2026-10-04，T01b 实测 210 轮）**：Jev **热状态下很快**——7 题一次请求 p50 384ms、p95 554ms，与官方宣传一致；单题、风险题单独问也都在 0.4 秒左右，延迟不随题目数增长。T01 的 6.4 秒和几次 4–6 秒的尖峰都出现在**冷启动**（进程第一次调用、空闲一段时间后的第一次调用、突发并发的第一批）。
- 更正：T01b 报告里"慢在 OpenRouter Decisions 路径"的结论与它自己的数据矛盾——A–D 四组全部走的就是 Decisions 路径，均约 0.4 秒；那次 6.3 秒的探针是冷调用。两条路径都可用，不切换。
- 最终配置：① L2 意图和风险**合并成一次 Jev 请求**（配置 A：比分开问 B+C 少一次调用、总成本更低、延迟相同；并行拆分 D 尾延迟更差）；② 服务启动时预热一次，之后每 4 分钟保温一次（`JEV_KEEPALIVE_MS`，成本约每小时 $0.001）；③ Jev 单次尝试 3 秒超时，失败降到 LLM，`decide()` 总预算 9 秒；④ 兜底分类模型换成 `deepseek/deepseek-v4-flash`（准确率 96.7%、更便宜），所有 LLM 默认关闭思考。
- 对演示叙事：「又快又省」成立——L1 毫秒级；L2 约 0.4 秒、每条约 ¥0.0004；不用 Jev 而用 LLM 做分类要 2.6 秒；L3 多步编排数秒。看板如实展示。
